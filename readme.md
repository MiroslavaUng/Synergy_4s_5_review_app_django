## 1. Анализ по критериям

### Функциональность

*   **Обоснование:** Программа полностью выполняет поставленную задачу. Реализована главная страница с формой, данные корректно сохраняются в базу данных через модель `UserName`. Функция-представление (View) правильно обрабатывает как успешные отправки (выводит приветствие), так и пустые поля. CSRF-защита работает корректно.

### Производительность
*   **Оценка:** Высокая (для текущего масштаба).
*   **Обоснование:** Используется встроенная SQLite, которая моментально обрабатывает одиночные запросы на вставку и чтение. Сервер разработки Django (`runserver`) мгновенно отдает HTML-шаблон. Функция `getAge` (в контексте других задач) и простые запросы к БД выполняются за доли миллисекунд.

### Удобство использования (Юзабилити)
*   **Оценка:** Хорошая.
*   **Обоснование:** Интерфейс минималистичен и понятен. Использован современный дизайн (градиентный фон, центрирование Flexbox, полупрозрачные элементы). 
*   **Проблема:** Нет мгновенного автоответа без перезагрузки страницы (что нормально для классического Django).

    **Разъяснение по архитектуре взаимодействия:** <br>Классический Django работает по схеме «запрос-ответ» (Server-Side Rendering). Это означает, что при отправке формы (нажатии на "Submit") браузер отправляет данные на сервер, после чего происходит полная перезагрузка страницы: сервер генерирует новый HTML-код с уже добавленным приветствием и возвращает его пользователю. Мгновенного автоответа без перезагрузки (как в SPA-приложениях или при использовании технологий AJAX/fetch) здесь нет. Для реализации динамического обновления интерфейса потребовалось бы писать дополнительный JavaScript-код, что избыточно для данной задачи. Классический подход с перезагрузкой является стандартным, надежным и абсолютно нормальным для подобных веб-приложений, так как он обеспечивает простоту поддержки и безопасность «из коробки».

### Безопасность
*   **Оценка:** Средняя (базовая).
*   **Обоснование:** Реализована обязательная защита от CSRF (тег `{% csrf_token %}`). Django ORM защищает от SQL-инъекций. 

    **Разъяснение: Защита от CSRF (тег `{% csrf_token %}`)** <br>CSRF (Cross-Site Request Forgery — межсайтовая подделка запросов) — это атака, при которой злоумышленник заставляет браузер пользователя отправить нежелательный запрос на сайт, где пользователь уже авторизован. При использовании тега `{% csrf_token %}` Django генерирует уникальный случайный токен и вставляет его в скрытое поле формы. При отправке формы сервер строго проверяет совпадение этого токена. Если запрос пришел с чужого вредоносного сайта, токен будет отсутствовать или не совпадет, и Django отклонит запрос, выдав ошибку 403 Forbidden. Это надежно защищает данные пользователя от несанкционированных действий.

    **Разъяснение: Защита от SQL-инъекций (Django ORM)** <br>SQL-инъекции — это атаки, при которых злоумышленник пытается внедрить вредоносный SQL-код через поля ввода (например, вместо имени вводит конструкцию `' OR '1'='1`), чтобы получить доступ к чужим данным или удалить их. Django ORM (Object-Relational Mapping) полностью абстрагирует работу с базой данных. Когда разработчик передает переменную (например, `UserName.objects.create(name=name_input)`), ORM автоматически экранирует все специальные символы и формирует безопасный SQL-запрос «под капотом». Благодаря этому любой введенный текст воспринимается исключительно как строка данных, а не как исполняемая команда, что делает приложение неуязвимым для подобного вида атак.

*   **Проблема:** Секретный ключ `SECRET_KEY` и режим `DEBUG = True` хранятся прямо в `settings.py`, что недопустимо для реального продакшена. Введенные имена выводятся без экранирования (хотя Django-шаблоны по умолчанию экранируют HTML, стоит учитывать риски XSS). В текущую MVP (минимально жизнеспособный продукт) проекта данная реализация не заложена; необходимые доработки по безопасности будут выполнены при полноценной публикации на промышленный (production) стенд.
    
    **Разъяснение: Секретный ключ `SECRET_KEY` и режим `DEBUG = True` в `settings.py`**
    <br>В файле настроек по умолчанию включен режим отладки (`DEBUG = True`) и хранится `SECRET_KEY` (ключ для шифрования токенов и сессий). Режим отладки полезен при разработке, так как подробно показывает ошибки, но на реальном сервере он становится уязвимостью: при любом сбое хакер увидит структуру путей, настройки базы данных и фрагменты кода. Открытый `SECRET_KEY` в коде (особенно если код выложен на GitHub) позволяет злоумышленникам подделывать сессии пользователей. В продакшене `DEBUG` обязательно переводят в `False`, а `SECRET_KEY` и другие пароли выносят в скрытые переменные окружения (файл `.env`), который не попадает в репозиторий.

    **Разъяснение: Вывод имен без экранирования и уязвимость XSS**
    <br>XSS (Cross-Site Scripting) — это атака, при которой злоумышленник вводит в форму не просто имя, а вредоносный JavaScript-код (например, `<script>alert('Взлом!')</script>`). Если сервер сохранит и выведет этот код на страницу без обработки, браузер других пользователей его выполнит, что может привести к краже паролей и данных. Django-шаблоны по умолчанию защищают от этого: все переменные автоматически экранируются (опасные символы вроде `<` и `>` превращаются в безопасный текст и не выполняются). При выводе пользовательских данных всегда нужно помнить о рисках XSS и не отключать базовую защиту без острой необходимости.

Таким образом, для учебного прототипа ручная валидация была выбрана как осознанный компромисс ради наглядности, но при росте проекта этот код потребует обязательного рефакторинга с переносом логики в `forms.py`.

    <br> **Разъяснение**: Отсутствие unit-тестов в текущей реализации обусловлено спецификой учебного MVP-проекта: функционал приложения минимален (одна форма и простая модель), поэтому ручная проверка в браузере занимает меньше времени, чем настройка тестового окружения. Так как на этапе создания прототипа не планировалось сложных интеграций и частого рефакторинга, разработка велась по принципу быстрого достижения видимого результата, а не обеспечения долгосрочной надежности кода. Однако такой подход является осознанным компромиссом: при масштабировании проекта или добавлении новой бизнес-логики отсутствие автоматических тестов станет критическим фактором риска, требующим немедленного написания тестов для предотвращения регрессионных ошибок.

## 2. Выявленные проблемы и способы их решения

В ходе анализа были выявлены следующие слабые места, которые следует улучшить в рамках дальнейшего развития проекта:

**Проблема 1: Отсутствие автоматических тестов.**
*   *Решение:* Написать unit-тесты в файле `myapp/tests.py`. Протестировать модель `UserName`, а также View-функцию (проверить, что GET-запрос возвращает код 200, POST с пустым полем возвращает ошибку, а POST с именем создает запись в БД).

**Проблема 2: Небезопасные настройки (`DEBUG = True` и `SECRET_KEY` в коде).**
*   *Решение:* Использовать библиотеку `python-dotenv` для выноса секретных данных в файл `.env` (который добавлен в `.gitignore`). В продакшене установить `DEBUG = False` и настроить `ALLOWED_HOSTS`.

**Проблема 3: Использование SQLite и сервера `runserver` для продакшена.**
*   *Решение:* Для реального размещения перейти на СУБД PostgreSQL, а сервер разработки заменить на Gunicorn (для Linux) и Nginx в качестве веб-сервера/прокси.

    **Разъяснение: Проблема с базой данных (SQLite)**
    <br>SQLite — это легкая файловая база данных, используемая в Django по умолчанию, которая идеально подходит для локальной разработки благодаря своей простоте (все данные хранятся в одном файле). Однако она категорически не подходит для реального продакшена из-за отсутствия поддержки высокой конкурентности: при одновременном обращении большого количества пользователей база данных блокируется, что приводит к очередям и зависанию сайта. Для реального размещения необходимо перейти на полноценную клиент-серверную СУБД, такую как PostgreSQL, которая спроектирована для надежной обработки тысяч параллельных запросов и обеспечения сохранности данных.

    **Разъяснение: Проблема с веб-сервером (runserver)**
    <br>Встроенный сервер разработки `runserver` отлично справляется с задачей локального тестирования, но абсолютно не пригоден для публикации в интернете. Сам Django предупреждает об этом желтым текстом при запуске. Этот сервер небезопасен, обрабатывает запросы последовательно (из-за чего страница будет загружаться медленно при наличии хотя бы нескольких пользователей) и не предназначен для отдачи статических файлов (картинок, стилей) под высокой нагрузкой. Использование `runserver` на реальном сервере делает приложение медленным и уязвимым для атак.

    **Разъяснение: архитектура для продакшена (Решение)**
    <br>Правильная архитектура для боевого сервера разделяет обязанности между двумя компонентами. Вместо `runserver` используется WSGI-сервер (например, Gunicorn для Linux), который запускает несколько копий Django-приложения для быстрой обработки Python-кода. А перед ним ставится веб-сервер Nginx, который встречает пользователей, моментально отдает статические файлы (CSS, изображения), защищает от атак и перенаправляет сложные запросы к Gunicorn. Такая связка (например, PostgreSQL + Gunicorn + Nginx) обеспечивает высокую производительность, безопасность и отказоустойчивость веб-приложения.

**Проблема 4: Ручная валидация ввода вместо Django Forms.**
*   *Решение:* Создать класс `NameForm(forms.Form)` в `forms.py`, который будет автоматически проверять на пустоту, максимальную длину и возвращать готовые HTML-формы. Это уменьшит количество кода во View и повысит безопасность.

**Проблема 5: Отсутствие функционала просмотра всех сохраненных имен.**
*   *Решение:* Можно добавить на главную страницу вывод всех сохраненных имен QuerySet: `UserName.objects.all()`. Для больших объемов данных внедрить пагинацию (постраничный вывод).
